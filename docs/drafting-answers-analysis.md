# 줄글 → 정식보고서: 정답 5건 비교 분석 (2026-10-03)

입력은 `samples/drafting/줄글_N_*.txt`(가상 문서)이고, 정답은 사용자가 사내 보고서처럼 직접 고쳐 쓴 docx 5건이다.
정답의 글자는 `정답_N_*.txt`에 옮겨 두었다. 앞 공백은 원본 그대로이고, 표는 칸을 탭으로, 칸 안의 줄을 " / "로 이었다.
제목 아래 그림 선은 사용자 설명에 따라 밑줄로 본다.

## 1. 요약

- 정답은 원문 문장을 **하나도 그대로 쓰지 않았다**. 글자 수는 원문의 62~75%로 줄었다(공백 제외 380→235, 457→342, 404→292, 404→286, 402→290).
  지금 `draft`는 "원문 문장을 그대로 두고 배치만 한다"로 설계되어 있어서 정답과 가장 크게 어긋나는 부분이다.
- 구조는 유형마다 다른 고정된 틀을 따른다. 현황, 검토, 결과, 계획, 이슈·건의 보고 모두 "사실 → 판단·대안 → 결론·조치" 순서다.
- 서식은 formal 서식과 대부분 같다. 다른 점은 다음 다섯 가지다.
  - ※·`*`의 위치
  - "항목명 : 값"의 굵기와 쌍점 맞춤
  - 표 서식(12pt·장평 90%·왼쪽)
  - 끝맺음 "- 이 상 -"
  - 주석 모양(검은 글씨, 본문 크기)

## 2. 구조 (보고서 유형별 틀)

| # | 유형 | 정답 구조 | 맨 위 단계 |
|---|---|---|---|
| 1 | 현황 보고 | □ 채용 목표 : 값 / □ 채용 현황 : 값 (※ 비교, - 세부 → ∙ 직군별, ※ 원인) / □ 추진 방향 (- 조치 2개, → 목표, ※ 후속) | □ |
| 2 | 방안 검토 | 1. 배 경 (□ 요지, - 근거, ※) / 2. 검토 방안 (**표**: 1안·2안 × 장점·단점) / 3. 추진 방향 (□ 결론 한 문장) | 1. |
| 3 | 결과 보고 | □ 운영 경과 (- 기 간 / 대 상 / 참 여) / □ 주요 결과 (- 등급별 / 부서별 / 조정건) / □ 향후 계획 (①②③) | □ |
| 4 | 추진 계획 | □ 대 상 : 값 / □ 일 정 : 값 / □ 세부 프로그램 (- 항목 : 값 ×3) / □ 소요 예산 / ※ 기타 사항 | □ |
| 5 | 이슈·건의 | □ 배경 및 이슈 (- 핵심, ∙ 근거, ※ 경쟁사) / □ 검토 가능(안) (①②③ 안 : 평가) / □ 건의 사항 (- 제안, ※ 확인 필요) | □ |

정답에서 읽히는 규칙:

- **절은 2~5개이고 이름이 정해져 있다.** 배경·현황·운영 경과·주요 결과 / 검토 방안·검토 가능(안) / 추진 방향·건의 사항·향후 계획. 끝 절은 늘 결론·조치다.
- **"1." 단계는 대안 비교 표가 있는 문서(2)에만** 쓰였다. 나머지는 □가 맨 위 단계다.
- **대안이 둘이면 표, 셋이면 ①②③ + 쌍점**으로 썼다. 표는 장점·단점 비교이고, ①②③은 "안 : 비용·난점"이다.
- **결론은 앞의 대안 번호를 다시 부른다**(5: "우선 연말에 ① …, 내년부터는 ② …", 2: "1안 우선 … 2안 경우 …").
- **목표나 결과는 "→" 줄**로 쓴다(1: "→ 설계 인력 4명 추가 채용 목표(~10.15일)").
- **단서·면책·후속 일정은 ※ 줄**이다. 정답 5건에서 ※ 9줄, `*` 2개가 나왔다.
- **사실 나열은 "항목명 : 값"**이다(1 □, 3 -, 4 □·-, 5 ①②③). 두 글자 항목명은 가운데를 띄운다: 기 간·대 상·참 여·일 정, 절 제목 "배 경".

## 3. 문장 변환 (원문 → 정답)

| 규칙 | 예 (원문 → 정답) |
|---|---|
| 화자·말투 삭제 | "저는 일단 … 제안드립니다" → "우선 …" / "보고드립니다", "~로 보입니다" 삭제 |
| 명사·한자 종결 | "높게 나왔습니다" → "불만 高", "확인이 필요합니다" → "확인 必", "시행이 가능합니다" → "시행 可" |
| `~함/~임` 거의 없음 | 정답 전체에서 `~함`·`~임` 종결은 0건. 명사(추진·검토·조정·응답·희망·예정·필요)나 한자 한 글자로 끝낸다 |
| 한자 약어 | 高 中 現 可 必 時 順 內 人 月 (10종) |
| 숫자·날짜 | "10월 15일까지" → "(~10.15일)", "8월 22일부터 이틀간" → "8.22(토) ~23(일)", "9월 5일" → "9.5(토)", "300만 원" → "300만원" |
| 비율·변화 | "(67.5%)", "(기존 25% → 30%)", "15명 中 12명", "3회/人", "1회/月", "5명/팀", "4억원/년" |
| 고유명 일반화 | "A사는 … B사는 …" → "경쟁사 경우, … 하거나 …", "경쟁사 두 곳" → "경쟁사(2개)" |
| 해석 문장 삭제 | "팀장들이 … 보수적으로 한 결과로 보입니다", "S와 A는 조금 낮고 B가 높게" 삭제 (가이드 수치를 `*`로 나란히 두는 것으로 대신함) |
| 세부 수치 일부 삭제 | 1: "7명은 후보를 찾는 중", "3개월 넘게 공석 두 개" / 4: "6개 팀", "500만 원 늘었습니다" / 5: "연 3천만 원 개인 부담", "환율" |
| 사람이 **추가**한 정보 | 3: "(~12월말)" 기한(원문 없음), 요일 "(토)"(달력 계산), 1: "지원책 논의 예정", 2: "(R&D 업무 특성에 적합)"(원문 뜻을 줄인 것) |

## 5. `draft` 설계에 주는 시사점

지금 설계(원문 문장 그대로, LLM은 배치만)로는 문장 변환(3절)을 하나도 재현하지 못한다. 대안은 셋이다.

- **A안 — 배치 + 규칙 압축**: 배치는 LLM, 문장은 파이썬 규칙(명사 종결, 한자 약어 사전, 숫자·날짜 정규화, 화자 표현 삭제)으로 줄인다.
  사실이 바뀔 위험은 가장 낮다. 다만 해석 삭제, 고유명 일반화, "항목명 : 값" 만들기는 규칙으로 못 한다. 정답과 가장 멀다.
- **B안 — 묶음별 LLM 재작성 + 파이썬 검증 (추천)**: LLM이 묶음마다 개조식 줄(항목명 : 값, 명사·한자 종결)을 쓴다.
  파이썬은 다음 다섯 가지를 확인한다.
  - 숫자: 결과의 숫자가 모두 원문에 있어야 한다. 날짜 표기 차이(10월 15일 ↔ 10.15)는 정규화해서 비교한다.
  - 한자: 약어 사전 밖의 한자는 막는다.
  - 기한·날짜: 원문에 없는 기한·날짜는 넣지 않는다. 3의 "(~12월말)" 같은 기한은 사람만 넣을 수 있다.
  - 빠진 수치: 원문에서 빠진 수치를 `--report`에 남겨 사람이 고르게 한다.
  - 대안: 대안이 2개면 표, 3개 이상이면 ①②③으로 쓴다.
- **C안 — LLM 자유 작성**: 정답에 가장 가깝게 쓸 수 있다. 하지만 3의 "(~12월말)"처럼 없는 정보를 만들 위험이 있고 검증 수단이 약하다.

채점(정답 대비): 절 이름 일치, 단계별 줄 수, 원문 수치 보존·삭제, 줄 종결 형태, 한자 약어 사용률, 글자 수 비율(정답 62~75%).

## 6. 확인이 필요한 것

1. □ 바로 아래 - 의 간격: 12pt(6곳)와 6pt(4곳)가 섞여 있다. "□ 제목 → -"는 12pt, "□ 요지 문장 → -"는 6pt로 나누면 되는가?
2. ※ 크기: 정답은 14pt인데 formal은 12pt(5차에서 사용자가 정한 값)다. 정답이 우선인가?
3. `*` 주석: 정답은 검은 글씨 12~14pt인데, 실측 8건은 파란 10pt 텍스트 상자였다. 둘 다 쓰는가?
4. 표: 정답은 왼쪽 정렬 + 들여쓰기 0.44cm, 장평 90%이고 formal은 오른쪽 정렬(6차에서 사용자가 정한 값)이다. 어느 쪽인가?
5. 4번 제목의 "차레대"는 오타로 보았다("차세대").
