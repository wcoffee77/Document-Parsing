## 4. 새로 해야 할 일 (우선순위)
**A. 먼저 확인 (사용자에게 물을 것, 코드 변경 전)**
1. d2.docx를 만든 정확한 명령(`draft`인지 `convert`인지, 옵션)과 `git log -1 --oneline` 결과(최신은 `7eeebbc` 이후여야 함). 구버전이면 pull 후 재실측만으로 상당 부분 해소될 수 있다.
2. 터미널 출력 끝의 `· …` 노트와 `--report` 파일의 '형식 오류/검증/줄임말/내용 보강/이해 불가' 줄 — 어떤 점검이 몇 번 돌았는지(원문 글자 없음).

**B. 터미널 경로를 eval과 같은 기준으로 만들기 (코드)**
3. `doc2report draft`가 끝에 **핵심 요약**(분량·방식·대안표·번호절·수치누락·줄임말·형식오류 횟수·검증회차)을 한 줄 블록으로 출력 — 지금은 eval에만 있어 사용자가 d2를 눈으로 읽어야만 판단 가능. `eval_drafting._brief`를 공용 함수로 옮길 것.
4. **실행마다 결과가 달라지는 문제**: `draft --runs N`(기본 1~2) — 같은 입력을 N번 돌려 검증 문제 수(사실·형식·구조·줄임말·누락)가 가장 적은 후보를 채택하고, 나머지 후보의 차이를 report에 남긴다.
   (온도 0이어도 서버 배치 때문에 달라질 수 있음 — 추정.)
5. `doc2report convert`에 입력이 줄글 txt이면 `draft` 쓰라는 경고 한 줄(또는 `--draft` 옵션)로 경로 혼동을 막는다.

**C. 품질 (사용자 지적 미해결분)**
6. **표 칸 간결화**: 칸 안 한 줄 32자 상한은 넣었지만 실측 전. 정답은 항목 최대 약 32자·조건 하나·'/'로 끊은 짧은 명사구. 칸 항목이 길면 줄 단위로 줄여 쓰는 수리(`_shorten_cell`, 사실·수치·절 유지 검증 후 채택)를 추가할지 실측 후 결정.
7. **줄임말('몰아일')**: `coined_words`가 건2 결과에서 잡힌 것은 확인했지만 재등장 → 재작성·수리 후에도 남는지 실측. 남으면 지시문에 금지 예시 보강 대신 **원문 어구를 그대로 인용하는 방식**(`몰아서 일하는` → `집중 근무`처럼 사전 낱말로만) 사전 `rules/drafting.yaml::coined_fix` 같은 규칙 매핑을 검토.
8. **절 구성**(1. 배경 / 2. 검토 방안 / 3. 추진 방향)이 □ 두 개로 뭉개진 문제: `번호 절이 없음` 점검의 재실측. 안 풀리면 대안 비교 문서는 **파이썬이 뼈대(1·2·3절 + 표 자리)를 먼저 세우고 LLM은 절 내용만 채우는** 2단 호출로 전환(규칙이 뼈대, LLM은 짧은 작업 — 로드맵 원칙 1).
9. 건1 분량 편차와 건3 분량 "799%"는 오기 여부 확인(79%면 기준 +2%p).

**D. 이후 (사용자 우선순위 — C가 끝난 뒤)**
10. 여러 보고서 → 요약·핵심 정리 → 새 보고서(`docs/roadmap-drafting.md` B단계). 입력 수·형식·산출물 종류·샘플/정답 보고서를 사용자에게 먼저 받을 것.
